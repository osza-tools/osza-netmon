## 1. Executive summary

The full Appendix D protocol ran on the T-106 netns harness (used as-is: the
responder binary, its config format and its seed scheme are the T-106
deliverables, unmodified) plus one observation stand-in for the Owner's
client-isolated Wi-Fi. Every scenario × profile × rate × passes cell of the
ADR-011 experiment space — 108 grid cells on S1/S2/S4 (324 cycles), 9 unique S9
cells (each measured three times with identical results — an unplanned determinism re-check), 4
ten-cycle periodic runs — reached **≥ 95% cumulative recall by cycle
3 on profiles P0–P2**, most at 100%. The ADR-011 defaults (100 pps, 2 passes
initial, 1 pass periodic, sender = interface IP) meet the G-1 metric with
margin and meet NFR-02 (worst /24 cycle 7.6 s vs the 10 s budget); lowering
the rate to 50 pps **breaks NFR-02 under P3** (12.6 s), so the default rate
is re-pinned from data. Unicast refresh works (20 packets vs 486 for a /24
sweep) but cannot see MAC rotation (kernel stacks drop requests addressed to
a stale MAC; measured 0 of 10) and is **not adopted**. The interim
`pnet_datalink` transport's `ETH_P_ALL` + software-filter cost measured at
**≤ 1.8 µs per non-ARP frame** (+10 ms CPU over a 7.4 s scan at 800 pps of
background traffic, zero recall impact, zero rejected replies) while the
safe `ETH_P_ARP`-binding alternative requires `unsafe` or new dependencies —
ADR-009 accepts the interim selection. `/proc/net/arp` and netlink
`RTM_GETNEIGH` yield **the same entries**; netlink's extra states (STALE /
REACHABLE, both observed) do not map to the cycle-based aging model and do
not justify a dependency — ADR-010 keeps `/proc/net/arp`. The isolated-Wi-Fi
stand-in completed cleanly in both privilege modes with the honest
limited-visibility output (2 of 253 targets answered). The declared gap
R-15 (real wired LANs, non-isolated Wi-Fi) remains open and is restated in
§9.

### 2.2 The T-106 harness, used as-is

`tests/netns/` was **not modified** (task card §4). The campaign's binary,
`examples/poc_measure.rs`, builds the same lab topology as
`tests/netns/lab.rs` (veth pair in the wrapper namespace, device side moved
into a nested `unshare --net` child by PID, RFC 5737 addresses,
`addrgenmode none`, `02:…` synthetic MACs) and **re-execs the unmodified
T-106 test binary in `--responder` mode** with a generated
`responder.conf` in the documented T-106 format (`tests/netns/config.rs`).
Consequences:

* the impairment semantics (seeded SplitMix64 chain: ignore-first → drop →
  fraction → delay), the answer table and the receive log are exactly the
  ones behind the S8/S9 baseline;
* the seed scheme is the T-106 one (`MEASURE_BASE + profile index`; S9
  variants `+100 + index`), so every overlapping cell uses the same seed as
  the baseline — the defaults cell (100 pps, 2 passes) reproduces the
  T-106 baseline cell-for-cell (e.g. S4/P0: 100% / 14 packets / 1131 ms
  sweep / seed 2129465441, identical to `--measure`);
* the S8/S9 baseline itself was re-produced with the T-106 `--measure`
  entry point twice (runs `t105-base-a`/`t105-base-b`, 45 records each);
  all compared fields matched exactly (determinism check, §2.4).

T-105 additions beyond the T-106 vocabulary (all serialized in responder
configs and recorded per run): a fixed-delay impairment (`late`), background
non-ARP frame injection from the device side, device→host UDP traffic
(neighbor experiment), and a pinned device-side veth MAC (unicast
experiment). The impairment parameters of every lab are in the artifacts.

### 2.3 Metric definitions (Appendix D per-run record)

Every run records: date, network type, scope size, mode, transport, rate,
passes, sender IP variant, known devices, devices discovered per cycle,
extras, time to first device, sweep duration, packets sent, replies
received/rejected by reason, CPU time, and notes. Method for each:

| Field | Method |
|---|---|
| date | UTC at record time (`YYYY-MM-DDTHH:MM:SSZ`, no dependency) |
| network type | `netns synthetic (veth pair, user namespaces)` — the topology of §2.2 |
| scope size | `Ipv4Net::host_count()` of the lab subnet |
| mode | `active` (ARP sweep), `active (unicast refresh)`, `read-only`, `observation` |
| transport | production `LinuxArpTransport` (pnet_datalink 0.35.0, `ETH_P_ALL` + software EtherType filter); the transport experiment wraps it in a counting pass-through (`CountingTransport`, §5.1) |
| rate / passes | scanner arguments (clamped 1–500 pps, 1–3 passes by `ArpScanner`) |
| sender IP variant | interface address, or `0.0.0.0` via `ArpScanner::with_probe_sender_ip` (RFC 5227 probe form) |
| known devices | the lab's ground truth (kernel-answered addresses + responder answer table) |
| discovered (per cycle) | distinct accepted-observation IPs of that scan |
| recall (cumulative %) | \|discovered ∩ known\| / \|known\| × 100, cumulative across the cell's cycles |
| extras | \|discovered − known\| |
| time to first device | first sink callback minus scan start (ms) |
| sweep duration | responder-observed span of the cycle's requests: last − first + one pacing interval (ms) |
| packets sent | scanner counter `requests_sent` |
| replies received/rejected | T-103 `ArpReplyCounters`, all 14 reasons tallied per record |
| CPU time | `utime+stime` of `/proc/self/stat` across the scan window (ms, 10 ms granularity) |
| responder drops | `DROP` records in the responder log attributable to the cycle |
| notes | per-experiment context (impairment mechanism, halves, seeds) |

### 2.4 Determinism

The T-106 `--measure` baseline was run twice (A/B): **45 records, 0
differences** across recall, packets, accepts, duplicates, drops and
rejection tallies — matching the T-106 report's own zero-variance claim on
this machine. The campaign grid inherits the property (same seeds, same
request order per address); e.g. the S2/P1 1-pass cell shows 94.0% at
cycle 1 and 100% at cycle 3 at **all three rates**, as the per-request
impairment decisions depend on arrival order, not wall-clock timing.

## 4. ADR-011 experiments (probe strategy)

### 4.1 Rate (50 / 100 / 200 pps)

Recall is **rate-independent** at every profile and pass count (the
impairment decisions depend on request arrival order, not timing — see the
identical recall columns across rates in §3.2). Rate only buys or spends
time:

| Rate | S2 sweep (1 pass) | S2 elapsed (2 passes, worst profile P3) | NFR-02 (≤ 10 s) | Packets per /24 pass |
|---|---|---|---|---|
| 50 pps | 5082 ms | 12641 ms | **violated under P3** | 253 |
| 100 pps | 2552 ms | 7589 ms | met (24% margin) | 253 |
| 200 pps | 1284 ms | 5061 ms | met (49% margin) | 253 |

The packet count per pass is the same at every rate (253 on a /24 — the
whole target set); rate only changes the offered load and the duration.
50 pps doubles the discovery latency of the *first* cycle and breaks the
NFR-02 budget under impairment; 200 pps halves latency but doubles the
instantaneous load on the network for recall the data shows is identical.
**100 pps stays** (the ADR-011 default), now re-pinned from measurement.

### 4.2 Passes (1 / 2 / 3) and periodic rediscovery

Cycle-1 recall on S2 (the hardest gated scenario, all rates identical):

| Passes | P0 | P1 | P2 | P3 (not gated) | Packets (P2) |
|---|---|---|---|---|---|
| 1 | 100% | 94% | 80% | 0% | 253 |
| 2 | 100% | 100% | 95.6% | 75.6% | 306 |
| 3 | 100% | 100% | 98.4% | 96.0% | 320 |

* **2 passes** (the initial-scan default) reaches ≥ 95.6% within the *first*
  cycle on P0–P2 — the "first 60 seconds" UX (plan §3.2) is served.
* **3 passes** adds ~48% more packets for ≤ 2.8 percentage points of
  cycle-1 recall and no cycle-3 gain. Not justified.
* **1 pass** is below 95% in cycle 1 under P2 (80%) but converges: the
  ten-cycle periodic runs (100 pps, 1 pass) show S2/P2 at 80% → 95.6% →
  99.2% → **100% by cycle 4**, and S2/P3 (sleepy) at 0% → 75.6% → 94.8% →
  98.4% → 99.6% → **100% by cycle 6**. S1 reaches 100% by cycle 3 on both
  profiles. Periodic 1-pass rediscovery is confirmed as the right
  steady-state strategy (§3.2 periodic table).
* The pass-2 snapshot semantics (T-104 review F-6) are measured directly in
  §4.5.

**Decision inputs: keep 2 passes for initial scan and manual refresh, 1
pass for periodic rediscovery** — both sides now have measured recall and
cost curves.

### 4.4 Unicast refresh of known devices

Phases over two labs (S1 shape, P0, 100 pps; both device halves rotate
between labs A and B):

| Phase | What it measures | Packets | Accepted | Recall |
|---|---|---|---|---|
| U1 cold unicast refresh | do targets answer unicast ARP requests at all, before any sweep? | 20 | 20 | 100% |
| U2 broadcast sweep | the discovery baseline | 486 | 20 | 100% |
| U3 warm unicast refresh | refresh exactly the discovered set | 20 | 20 | 100% |
| U4 stale-MAC refresh (rotation) | refresh the pre-rotation set against the rotated lab | 20 | 10 | 50% |
| U5 broadcast sweep after rotation | recovery | 486 | 20 | 100% |

* Unicast refresh **works and is cheap**: 20 packets and 1.7 s versus 486
  packets and 7.4 s for the same 20 devices on the /24 (24× fewer packets).
  Both the kernel half (10/10) and the helper half (10/10) answer cold and
  warm unicast requests.
* But it **cannot see identity rotation**: after both halves rotated their
  MACs, the kernel half answered **0 of 10** — the kernel drops ARP
  requests whose Ethernet destination is a MAC it no longer owns (the
  frames are `PACKET_OTHERHOST`). The 10 replies in U4 all came from the
  helper half, whose raw-socket responder on veth still sees
  stale-destination frames — a **harness asymmetry** (real NICs filter
  unicast in hardware, so real devices would answer 0 of 20; §9, L-4). The
  broadcast sweep (U5) recovers all 20 devices with their new MACs.

**Decision inputs: unicast refresh is NOT adopted as a discovery or
refresh mechanism in 0.1.0.** It is blind to MAC rotation — exactly the
R-11 randomization scenario the plan calls out — and the broadcast sweep
cost it would save (253 packets per /24 pass, ~4 s) is inside every budget
the plan sets. It stays recorded as a backlog candidate for a future
"refresh known devices cheaply *in addition to* the periodic broadcast
rediscovery" mode.

### 4.5 Pass-2 snapshot semantics (T-104 review F-6)

The task card requires the experiment design to account for the pass-2
snapshot: the non-responder set is frozen at pass start, so a late answer
is re-probed once. Measured with a fixed 2500 ms reply delay (longer than
the 1 s pass gap) on the S1 shape, 2 passes at 100 pps:

* The responder log shows **233 of 253 addresses probed twice** — their
  pass-1 replies (2500 ms late) had not arrived when pass 2 snapshotted
  the non-responder set, so pass 2 re-probed them; 20 addresses were
  probed once (their answers arrived before the snapshot: the 10 kernel
  answers are immediate, plus the 10 first-pass helper answers that landed
  inside the window).
* All 20 known devices were still discovered within the single scan
  (100% recall, 486 packets): the late pass-1 replies were accepted during
  pass 2 (the solicited set spans the whole scan), and the re-probe's own
  reply (another 2500 ms later) landed inside the 1.5 s listen window or
  was simply redundant.
* No address was probed more than twice in a 2-pass scan — the snapshot
  semantics bound the re-probe count at exactly one per late answer.

The behavior matches the F-6 analysis: late answers cost at most one extra
probe each, never a miss.

## 5. ADR-009 experiments (transport)

### 5.1 The `ETH_P_ALL` + software-filter cost (T-104 deviation 5)

The production transport (`pnet_datalink` 0.35.0) binds `ETH_P_ALL`, so
its socket receives every frame on the interface; the scanner drops
non-ARP frames in software before validation (FR-DS-07: nothing is
collected). Cost measurement: the same S1 scan (2 passes, 100 pps) with a
counting wrapper around the production transport, under controlled
non-ARP background traffic (60-byte EtherType `0x1234` frames from the
device side at 0–800 pps):

| Background | Non-ARP frames delivered to userspace | CPU (ms) | Elapsed (ms) | Accepted | Extras |
|---|---|---|---|---|---|
| 0 pps | 0 | 90 | 7397 | 20 | 0 |
| 50 pps | 368 | 100 | 7385 | 20 | 0 |
| 200 pps | 1455 | 90 | 7385 | 20 | 0 |
| 800 pps | 5613 | 100 | 7379 | 20 | 0 |

* The per-frame software-filter cost is bounded by the CPU delta: at the
  harshest point measured, **+10 ms of CPU per scan for 5613 filtered
  frames ≈ 1.8 µs per frame** (and the 90↔100 ms scatter at lower rates is
  within the 10 ms tick granularity of `/proc/self/stat`). Scan wall time
  and recall are unaffected at every background rate.
* A realistic small-network broadcast/multicast load (tens of pps) costs
  well under 1 ms CPU per scan — three orders of magnitude inside the
  NFR-04 idle budget, and the app reads the socket only during scans.
* One structural observation from the unicast experiment: an `ETH_P_ALL`
  socket that sits unread while traffic flows (between scans) accumulates
  a kernel-side receive backlog which the next scan's receive loop drains
  before fresh frames (measured: ~300 queued frames after a 7.4 s sweep).
  This is bounded by the socket buffer and costs only the drain time; it
  is noted as inherent to the interim transport, not as a defect.

### 5.2 The `ETH_P_ARP`-binding alternative

A safe `ETH_P_ARP`-bound `AF_PACKET` socket cannot be written in our
code: `pnet_datalink` hardcodes `ETH_P_ALL` for `ChannelType::Layer2`
(verified in the vendored source), and the safe alternatives cannot both
create and bind the socket — in `nix 0.31.3` the `LinkAddr` type wrapping
`sockaddr_ll` is crate-private with no `ETH_P_ARP` protocol variant, and
`socket2 0.6.3`'s raw `SockAddr` constructors are `unsafe` (T-104's
independently source-verified finding, restated in ADR-009). So the
alternative was measured at the kernel level with a witness: a Python
`AF_PACKET` socket bound with `ETH_P_ARP` (dev-only measurement tooling;
no project code, no dependency) counting its deliveries over the same
windows:

| Background | Production `ETH_P_ALL` socket saw | `ETH_P_ARP` witness saw |
|---|---|---|
| 0 pps | 20 ARP (the replies) | 20 ARP in |
| 50 pps | 368 non-ARP + 20 ARP | 20 ARP in, **0 non-ARP** |
| 200 pps | 1455 non-ARP + 20 ARP | 20 ARP in, **0 non-ARP** |
| 800 pps | 5613 non-ARP + 20 ARP | 20 ARP in, **0 non-ARP** |

The kernel-level EtherType filter works exactly as expected and would
eliminate 100% of the measured non-ARP delivery cost. (The witness also
demonstrates two socket-delivery details recorded for completeness: our
own outgoing requests are not delivered to the sending socket itself, and
an `ETH_P_ARP` socket does not receive the outgoing clones of frames sent
by an `ETH_P_ALL` socket — the clone's protocol is the sender's bind
protocol. Neither affects the receive path we use.)

### 5.3 Failure behavior: interface down/up mid-scan (Appendix D)

| Phase | Outcome | Elapsed | Detail |
|---|---|---|---|
| F1 link down mid-scan (at 1.0 s of 7.4 s) | `Failed: fatal transport failure: Unexpected poll event` | 1008 ms | the receive side observes the interface death within ~8 ms (pnet surfaces the socket's POLLHUP as a fatal transport error); 100 packets sent, all 20 observations so far retained, no hang |
| F2 recovery scan (link up again) | `Complete` | 7395 ms | full 20/20 recall on the next scan |
| F3 link down at scan start | `Failed: the network interface went down or was removed` (ENETDOWN, first send) | 0 ms | classified `InterfaceLost` by the typed error mapping |

The scan degrades honestly and boundedly in every phase: the outcome is
`Failed` (never a hang, never a false `Complete`), observations gathered
before the failure are kept (FR-DS-11), and recovery is a clean re-scan.
One wording note for ADR-009's consequences: the mid-scan failure reason
string ("Unexpected poll event") is pnet's; a native implementation would
map POLLHUP to `InterfaceLost`. Same classification, better message — a
follow-up note, not a defect.

### 5.4 §9.2 evaluation summary (ADR-009)

1. **Necessity**: no safe std/`nix`/`socket2` path to an `ETH_P_ALL`
   *or* `ETH_P_ARP` `AF_PACKET` socket exists without `unsafe`;
   `pnet_datalink` is the only approved-candidate library that opens,
   binds, sends and receives with no `unsafe` of our own.
2. **Maintenance**: `pnet_datalink` 0.35.0 (May 2024, slow cadence — the
   plan's own observation). The `ArpTransport` trait contains it to one
   module; ADR-009 records the containment and the measured swap cost.
3. **License**: MIT/Apache-2.0 — inside the `deny.toml` allowlist.
4. **`unsafe` footprint**: the library's own FFI is `unsafe` internally;
   our code has none (`unsafe_code = "forbid"`, CI-enforced).
5. **Transitives**: ipnetwork + pnet_base + pnet_sys + libc — small, no
   async runtime, no build-time network.
6. **MSRV**: compatible (locked tree verified at 1.89 per T-000).
7. **Constraints**: no runtime network, no build scripts fetching data.

The measured cost of the `ETH_P_ALL` compromise (§5.1) is negligible at
realistic rates and would only become material on networks with sustained
very high non-ARP broadcast volume; the alternative's safe implementation
requires a dependency the plan does not currently approve.

**Decision: accept `pnet_datalink` 0.35.0 as the production `ArpTransport`
(ADR-009: Accepted, provisional status lifted)** — the interim selection
becomes final on the measured evidence.

## 6. ADR-010 experiments (neighbor-table source)

### 6.1 What each source yields, over time

Lab: five kernel-answered devices (192.0.2.2–.6) sending one-way UDP to
the host for 10 s — the only kernel-level IP traffic — then silence.
Both sources sampled at t = 2, 12, 45, 75 s, then once more after a full
active ARP sweep:

| Sample | `/proc/net/arp` (production reader, T-102) | netlink `RTM_GETNEIGH` (via `ip neigh`) |
|---|---|---|
| t = 2 s (traffic running) | 1 entry: 192.0.2.2 | 1 entry: 192.0.2.2 = STALE |
| t = 12 s (traffic stopped) | 1 entry: 192.0.2.2 | 1 entry: 192.0.2.2 = STALE |
| t = 45 s | 1 entry: 192.0.2.2 | 1 entry: 192.0.2.2 = STALE |
| t = 75 s | 1 entry: 192.0.2.2 | 1 entry: 192.0.2.2 = STALE |
| after the active scan | 1 entry: 192.0.2.2 | 1 entry: 192.0.2.2 = **REACHABLE** |

### 6.2 What the experiment establishes

* **The entry sets are identical.** Every address present in one source is
  present in the other, at every sample point. Netlink's only addition is
  the state word.
* **The neighbor table yields peers that ARPed *us*, not peers that talked
  to us.** Only 192.0.2.2 — the source address of the first ARP
  resolution — appears, even though all five devices sent UDP throughout
  the traffic window: the device side resolves the *host* once (IPv4 ARP
  keeps one neighbor entry per destination, shared across source
  addresses), so the host only ever receives one ARP request. Receiving IP
  traffic does not populate the host's ARP table. The neighbor-table path
  is therefore exactly what the read-only fallback needs — the gateway and
  whoever initiated traffic toward us — and nothing more.
* **Our own active scans do not populate the table.** After the 2-pass
  sweep that discovered and accepted all 5 devices (the responder-less
  kernel half answering), the host's `/proc/net/arp` still contains only
  the pre-existing 192.0.2.2 row: raw-socket probes and replies do not
  create kernel neighbor entries (unsolicited replies with `arp_accept=0`
  are not cached — measured, not assumed).
* **The state word does not map to our model.** STALE persisted unchanged
  from t = 2 s to t = 75 s (both during traffic and 65 s after it), and
  REACHABLE appeared only after our scan's reply from .2 confirmed the
  entry — a kernel-internal transition. Our aging model is cycle-based
  (ADR-007) and our vocabulary deliberately avoids kernel state names
  (ADR-002: kernel `STALE` ≠ our `Idle`). The states carry no decision the
  0.1.0 design consumes.

### 6.3 Read costs

Production `/proc/net/arp` reader: ≈ 10 µs per read (mean of 200).
`ip neigh` spawn: ≈ 1.1 ms (mean of 20) — an *upper* bound for netlink
(a Rust client's `RTM_GETNEIGH` dump is a handful of syscalls, no process
spawn). Both are negligible next to a scan cycle; cost is not a
differentiator.

### 6.4 The dependency question

A netlink client in Rust means new dependencies: the realistic no-async
option is `netlink-sys` (0.9.0) + `netlink-packet-route` — two crates on
top of a sync socket layer (its async features are opt-in and stay off);
`rtnetlink` is deprecated in favor of that pair and historically pulled
async runtimes. Against that cost, the measured benefit is a state word
(§6.2) that the current aging model cannot consume, on a source whose
entry set is identical to `/proc/net/arp`.

**Decision: keep `/proc/net/arp` (ADR-010: Accepted, the T-102
implementation stands).** Netlink states remain backlog item §18.5,
revisitable if a future feature consumes reachability semantics (e.g. a
"kernel-verified" note in Details).
